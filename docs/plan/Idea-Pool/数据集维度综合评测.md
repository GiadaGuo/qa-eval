`docs/development/dataset-comprehensive-evaluation-plan.md`

## 三、核心架构原则：双入口、统一执行内核

系统应支持两种独立的用户操作模式：

### 模式 A：单指标快速评测（保留）

```text
指标库
  ↓
选择指标
  ↓
配置 Calculator、参数和规则
  ↓
选择数据集
  ↓
创建单指标 Contract
  ↓
执行
  ↓
查看单指标结果
```

适用于指标开发、Calculator 调试和专项质量检查。

**要求：尽可能保持现有页面、API 和操作流程兼容。**

### 模式 B：数据集综合评测（新增）

```text
Dataset Version
  ↓
创建综合评测
  ↓
选择多个 Metric
  ↓
分别配置 Calculator、参数、规则和阈值
  ↓
创建并发布多指标 Quality Contract
  ↓
Logical Evaluation Plan
  ↓
Physical Evaluation Plan
  ↓
Evaluation Run
  ↓
多个 StageRun + MetricResult
  ↓
RuleEvaluation + QualityIssue
  ↓
综合 QualityReport
```

适用于对整个数据集进行系统性质量评价。

**两种模式应共享现有 Contract、Planner、Executor、Result Service 等底层能力，不允许复制出第二套评测引擎。**

单指标 Contract 可以作为统一 Contract 模型中只包含一个 Metric 的特殊情况。

但不要为了统一而强制重写现有单指标前端流程。

## 五、第二项：Logical Plan 与 Physical Plan

这是本阶段重点。

### 5.1 审查现有 Physical Plan

请阅读实际实现，确认：

- Physical Plan 的生成入口。
- Physical Plan 的存储结构。
- Physical Plan 是否包含 Stage 列表。
- Stage 是否记录 Calculator、参数、输入和输出。
- Evaluation Run 如何加载 Physical Plan。
- Executor 是否支持多个 Stage。
- StageRun 与 MetricResult 如何关联。
- 失败时如何更新 Run 状态。
- 当前是否已经存在 Logical Plan 或类似抽象。

必须给出实际代码路径和函数名称。

### 5.2 设计 Logical Plan

Logical Plan 应根据多指标 Contract 生成可校验的逻辑执行计划。

至少表达：

- Contract 中需要评测的 Metric。
- 每个 Metric 对应的逻辑计算节点。
- 输入数据需求。
- 节点依赖关系。
- 节点输出及其对应的指标。
- 可并行与必须顺序执行的关系。

对于没有依赖的指标，可以生成彼此独立的节点。

**不要人为制造指标之间的依赖。**

需要区分：

- Metric 之间的业务依赖。
- Calculator 执行过程中的数据依赖。
- 共享预处理或中间结果的优化机会。

V1 可以不实现共享计算优化，但需要判断现有数据模型是否应预留依赖表达。

### 5.3 设计 Physical Plan

Physical Plan 将 Logical Plan 映射为可执行 Stage。

至少包含：

- Calculator ID、版本和 EntryPoint。
- 参数。
- 数据输入引用。
- Stage ID。
- 依赖 Stage ID。
- 输出及 Evidence 引用。
- 对应 Metric 和 Contract 配置的标识。

请判断现有 Physical Plan 能否直接扩展，避免重新建设。

### 5.4 编排策略

V1 优先采用最小可用方案：

- 多个独立 Calculator 可按拓扑顺序执行。
- 有真实依赖时才添加依赖边。
- 允许暂时使用现有单线程执行器。
- 不强制实现并行调度。
- 不引入 Celery、Kafka、Airflow 等新基础设施。

重点是**执行计划的正确性和可追溯性**，而不是吞吐量优化。

## 六、第三项：多指标执行与状态管理

请审查 EvaluationRunService、Executor、StageRun 和 MetricResult。

重点规划：

1. 一个 EvaluationRun 对应多个 StageRun。
2. 一个 Contract 对应多个 MetricResult。
3. 每个 StageRun 如何关联 Metric、Calculator 和 Plan Node。
4. 多个 Stage 的执行顺序。
5. 部分 Stage 失败时是否继续执行其他独立 Stage。
6. Run 最终状态如何确定。
7. Stage 执行失败与指标规则不通过如何区分。
8. 重试是否会重复写入 MetricResult 和 Evidence。
9. 如何避免重复计算或重复写入。
10. 如何保留现有单指标执行兼容性。

特别要求明确状态语义：

- Calculator 执行成功。
- Calculator 执行失败。
- 指标规则通过。
- 指标规则不通过。
- 指标不适用。
- 指标未执行。
- 指标因前置依赖失败而跳过。

如果现有状态枚举不支持某些语义，请分析是否需要扩展，而不是直接混用已有状态。

## 七、第四项：多指标综合评分与 Quality Report

当前单指标报告不能直接等同于综合质量报告。

请审查现有：

- MetricResult。
- RuleEvaluation。
- QualityIssue。
- IssueIndex。
- QualityReport。
- QualityResultService。

重点设计：

### 7.1 指标级结果

每个指标至少可追溯：

- Metric Code。
- Metric Definition Version。
- Calculator Version。
- 原始计算值。
- 归一化得分（如适用）。
- Rule Evaluation。
- QualityIssue。
- Evidence。
- 执行状态。

### 7.2 维度级聚合

根据现有高质量数据集评价指南的维度和权重，规划维度得分计算。

需要明确：

- 权重来源。
- 归一化规则。
- 分数方向。
- 不同量纲如何处理。
- 指标缺失时如何处理。
- 不适用指标是否参与分母。
- 执行失败时是否允许生成综合分数。

不得直接把不同指标的原始计算值相加或求平均。

### 7.3 数据集综合评分

规划综合质量得分与报告。

必须区分：

- 完整评测。
- 部分指标评测。
- 不适用指标。
- 未执行指标。
- 执行失败指标。

如现有标准没有明确某项聚合规则，应标记为待确认，不得自行发明官方评分规则。

### 7.4 报告下钻

目标结构：

```text
数据集综合报告
    ↓
评价维度
    ↓
指标
    ↓
MetricResult
    ↓
RuleEvaluation / QualityIssue
    ↓
Evidence
    ↓
SampleRecord
```

请检查当前已有下钻能力，尽可能复用。

## 九、测试场景与验收标准

至少规划以下四个测试场景。

### Case A：单指标回归

使用现有 `02080103` 指标。

验证原有：

`Metric → Contract → Run → Result → Report`

仍然正常工作。

### Case B：两个独立指标

一个 Dataset Version，包含两个不同 Metric 的 Contract。

验证：

- Contract 能成功发布。
- Logical Plan 包含两个计算节点。
- Physical Plan 包含对应 Stage。
- 一个 Run 能执行两个 Calculator。
- 生成两个独立 MetricResult。
- 报告能展示两个指标。

### Case C：多个指标部分失败

三个指标中，一个 Calculator 执行失败。

验证：

- 失败指标有明确状态。
- 其他独立指标按策略继续执行。
- Rule FAIL 不被误认为 Calculator ERROR。
- 报告明确标识不完整性。
- 不会生成误导性的完整综合评分。

### Case D：综合报告下钻

从维度得分进入指标详情，再查看对应 Evidence 和 SampleRecord。

验证每一层引用关系正确。

如当前仅有一个可用 Calculator，请在计划中说明测试夹具或新增最小 Calculator 的需求，不得用同一个指标伪装成多个不同指标。
