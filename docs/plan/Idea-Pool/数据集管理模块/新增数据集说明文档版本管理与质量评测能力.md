
# 架构评估任务：一键生成说明文档质量评测报告

## 一、需求重新定义

项目：`qa-eval` 数据集质量评测平台。

当前项目已有：

- Dataset / Dataset Version 管理
- Calculator Registry / Loader / Protocol
- Quality Contract
- Evaluation Run
- Metric Result
- Quality Report
- `.agents/skills/dataset-document-evaluator`

现在需要新增一项相对独立的产品能力：

**一键生成说明文档质量评测报告（Document Quality Report Generation）。**

请注意：本次需求不是新增一个普通 Calculator，也不是为说明文档开发另一套指标配置系统。

我希望用户能够：

1. 在数据集管理页面上传说明文档。
2. 独立管理说明文档版本。
3. 选择某个 Document Version。
4. 点击「生成质量评测报告」。
5. 系统自动完成说明文档的全部适用指标评测。
6. 查看包含逐项评分、评分依据、缺失内容、改进建议和综合得分的报告。

用户不需要手动选择 Metric Definition、Calculator Implementation、Quality Contract 或配置评测参数。

## 二、核心设计原则

### 1. 以报告生成作为业务目标

本功能的基本单位是一次完整的说明文档质量报告生成任务，而不是单个指标计算任务。

输入：

```text
Document Version
```

输出：

```text
Document Quality Report
├── 文档基本信息
├── 评测标准及版本
├── 各项指标评分
├── 评分依据与文档证据
├── 缺失内容与质量问题
├── 改进建议
└── 综合评分及结论
```

系统内部可以按指标逐项评测，但不需要对用户暴露指标注册、算子绑定或契约配置过程。

### 2. 不预设必须使用现有 Skill

项目中存在：

`.agents/skills/dataset-document-evaluator`

请审查该 Skill 的真实实现和能力。

它可以作为：

- 评测规则参考
- 现有算法实现参考
- Prompt 设计参考
- 评分 Schema 参考
- 可复用的执行逻辑

但不要默认平台必须调用 Skill，也不要默认它已经是最佳实现。

请比较以下技术路线：

- 直接复用现有 Skill 的核心能力
- 平台内置文档评测服务
- LLM 结构化评审
- 规则校验与 LLM 结合
- 其他更符合项目实际情况的方案

最终推荐一个适合当前 MVP、可维护且能稳定产出报告的实现方案。

### 3. 不强制经过 Quality Contract

本功能原则上不需要用户创建或配置 Quality Contract。

请优先评估是否可以直接采用：

```text
Document Version
      ↓
Document Quality Report Generation
      ↓
Document Quality Report
```

不需要为了复用现有架构而强行引入：

- Metric Definition 注册
- Calculator Implementation 注册
- Quality Contract 创建
- Logical Evaluation Plan
- Physical Evaluation Plan

如果某些已有基础能力适合复用，例如后台任务、状态管理、文件解析、报告存储或展示组件，可以选择性复用。

但不要为了统一而制造额外复杂度。

### 4. 保留说明文档独立版本体系

Document Version 归属于 Dataset，但版本序列独立于 Dataset Version。

例如：

```text
Dataset A
├── Dataset Versions
│   ├── v1.0
│   └── v2.0
│
└── Document Versions
    ├── v1.0
    ├── v1.1
    └── v1.2
```

每次报告生成任务必须绑定具体 Document Version。

上传新文档不能改变历史报告。

## 三、请审查现有项目

重点阅读：

1. `.agents/skills/dataset-document-evaluator` 全部相关文件。
2. 高质量数据集指南中说明文档相关指标定义。
3. 现有 Dataset / Dataset Version 领域模型。
4. 文件上传、存储和解析相关代码。
5. Evaluation Run 的异步任务执行机制。
6. Quality Report 的生成、持久化和展示机制。
7. 前端数据集详情页和评测结果页。

重点判断哪些现有能力值得复用，哪些会造成不必要的耦合。

## 四、评测流程设计

请设计一个自动化的说明文档评测流水线，参考但不限于：

```text
选择 Document Version
          ↓
读取原始文档
          ↓
文档解析与内容提取
          ↓
按照指南识别适用评测要求
          ↓
逐项评测与证据提取
          ↓
计算指标得分
          ↓
汇总综合评分
          ↓
生成质量问题与改进建议
          ↓
持久化质量报告
```

请重点研究：

### 4.1 文档解析

- 支持哪些文件格式？
- 如何提取段落、标题、表格等内容？
- 如何处理解析失败、空文档、扫描版 PDF？
- 如何保存解析结果及解析器版本？

### 4.2 指标评测

- 指南中的各项指标如何转化为可执行评分要求？
- 哪些适合确定性规则？
- 哪些需要 LLM 语义判断？
- 是否存在混合评测需求？
- 如何避免 LLM 凭空判断文档包含不存在的信息？
- 如何记录具体证据位置？
- 如何区分缺失、未适用、无法判断与不合格？

### 4.3 评分汇总

- 如何严格继承指南规定的指标和权重？
- 如何处理不适用指标？
- 如何处理评测失败或证据不足？
- 如何保证总分计算可解释？
- 是否需要设置最低证据要求？
- 如何避免 LLM 直接主观生成总分？

建议优先由程序根据逐项评分和指南权重计算综合分数，而不是让 LLM 自行给出一个总分。

### 4.4 报告生成

请设计稳定的结构化报告 Schema。

至少包含：

- report_id
- document_version_id
- evaluation_standard_version
- evaluator_version
- execution_status
- overall_score
- metric_scores
- evidence
- missing_items
- recommendations
- generated_at

每项指标应包含：

- metric_code
- metric_name
- score
- scoring_basis
- evidence
- missing_requirements
- evaluation_method
- status

以上仅为建议字段，请根据实际指南和 Skill 输出设计最终 Schema。

报告需要能够解释每项分数从哪里来，而不只是展示一个数字。

## 五、版本化与可复现性

需要明确区分三个版本：

1. Document Version：被评测的文档内容版本。
2. Evaluation Standard Version：高质量数据集指南及评分标准版本。
3. Evaluator Version：评测程序、规则、Prompt 或模型配置版本。

每次报告生成任务应冻结相关版本与配置。

如果使用 LLM，还应记录模型标识、Prompt 版本、必要的调用参数及结构化输出校验结果。

需要考虑：

- 相同文档重复评测是否允许？
- 评测方法升级后如何重新生成报告？
- 历史报告是否可以查看？
- 失败任务是否允许重试？
- 是否需要记录执行耗时和错误原因？

不要求保证 LLM 每次输出完全一致，但必须保证评测过程可审计、可解释。

## 六、前端产品设计

在现有数据集详情页增加两个 Tab：

```text
数据集详情
├── 数据集版本
└── 说明文档版本
```

说明文档版本 Tab 支持：

- 上传说明文档
- 查看版本列表
- 查看文档元数据
- 下载原始文档
- 删除未被引用的版本
- 一键生成质量评测报告
- 查看历史生成报告

推荐交互：

```text
说明文档版本 v1.2
       ↓
点击「生成质量评测报告」
       ↓
显示生成中 / 成功 / 失败
       ↓
点击「查看报告」
       ↓
展示各项评分、证据和建议
```

报告可以复用现有报告展示组件，但不要为了复用 UI 而强行改变本功能的领域模型。

## 七、请比较技术实现方案

至少比较：

### 方案 A：直接调用现有 Skill

分析实际可行性、运行环境依赖、开发成本、维护成本和风险。

### 方案 B：平台内置文档报告生成服务

独立负责文档解析、评测、评分和报告生成。

可复用现有底层基础设施，但不依赖 Quality Contract / Calculator Registry。

### 方案 C：混合实现

复用 Skill 中成熟的算法、规则或 Prompt，迁移到平台服务中，通过统一的报告生成流水线执行。

可以补充其他更合适的方案。

比较维度：

- 开发成本
- 代码复用程度
- 是否满足一键生成报告
- 是否需要 Agent 运行环境
- LLM 集成难度
- 结果可解释性
- 版本可追溯性
- 测试难度
- 长期维护成本
- 与现有平台的耦合程度

请明确推荐一个方案，并说明为什么。

## 八、与现有评测体系的关系

当前数据内容质量评测继续使用：

```text
Dataset Version
    ↓
Quality Contract
    ↓
Evaluation Plan
    ↓
Evaluation Run
    ↓
Metric Result
    ↓
Quality Report
```

说明文档报告生成可以采用：

```text
Document Version
    ↓
Document Report Generation Task
    ↓
Document Quality Report
```

两者不必共用完整执行链路。

但请评估未来是否能够在数据集综合质量视图中汇总：

- 数据内容质量评测结果
- 说明文档质量报告

重点考虑统一指标编码、评分口径、评测标准版本和结果引用。

不要为未来可能的综合评测提前建设复杂的跨系统编排器。

## 九、MVP 范围

请设计一个最小可落地版本，优先完成：

1. 说明文档上传与独立版本管理。
2. 选择文档版本，一键生成报告。
3. 自动完成已支持的说明文档指标评测。
4. 结构化保存各项分数和证据。
5. 计算综合评分。
6. 在前端展示报告。
7. 支持查看历史报告及失败原因。

不要求：

- 用户自定义指标
- 用户配置 Calculator
- 用户创建 Quality Contract
- 用户编辑评分权重
- 复杂 Agent 编排
- 多文档联合评测
- 跨数据集批量评测
