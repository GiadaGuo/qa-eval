
# Codex 任务：评估并规划 MySQL jhsjk_article 数据集综合质量评测 Demo

## 一、任务定位

你是当前 `qa-eval` 项目的技术负责人、系统架构师和开发实施规划者。

请先完整审查当前项目代码、数据库模型、API、前端页面、现有指标实现、Agent/Skill 机制以及 `docs/` 中的技术设计文档，再制定一个**今天能够完成开发、联调、演示并形成交付案例文档**的实施计划。

**本轮任务只做代码审查、方案评估与开发计划编写，不直接修改业务代码。**

本次目标不是重构整个质量评测平台，而是基于已有能力，打通：

**MySQL jhsjk_article → Dataset Version → Dataset Profile → Agent 指标推荐 → 多指标 Quality Contract → 用户确认 → Evaluation Plan → Evaluation Run → Metric Results → 综合质量报告 → Agent 推送整改建议**

最终需要交付：

1. 一个可以从前端实际操作的端到端 Demo。
2. 一个覆盖《高质量数据集建设指南》数据质量指标全维度的综合评测报告。
3. 一份《MySQL jhsjk_article 数据集质量评测案例》交付文档。
4. 可复现的测试、运行步骤及真实评测证据。

今天优先确保闭环，不追求所有高级能力一次性实现。

## 三、目标业务流程与每个环节的闭环要求

这部分是本次开发计划的核心。

**每个环节必须明确：用户操作、系统输入、后台处理、持久化对象、输出结果、前端反馈、验收标准。**

不能只写功能名称。

### Step 1：MySQL 数据集接入

目标：

用户在前端选择或接入 MySQL `jhsjk_article`，创建可评测的数据集版本。

需要检查：

- 是否已经支持 MySQL 数据源。
- 是否能选择表并创建 Dataset Version。
- 是否能够完成字段映射。
- 是否能够生成基本 Dataset Profile。
- 是否可以对现有数据集版本直接复用。

必须明确本次采用：

A. MySQL 原表直接读取；

B. 从 MySQL 导入并生成标准化数据快照；

或 C. 复用已有数据集版本。

请根据项目当前架构选择最小可行方案。

必须保证评测绑定确定的数据集版本和数据范围，避免数据源变化导致结果无法复现。

**闭环验收：**

前端能够进入 `jhsjk_article` 数据集详情页，看到具体版本、字段信息、记录数及基础画像。

**人工审核**：目前已经支持手动上传`jhsjk_article`对应的jsonl文件，当前步骤可以跳过。

### Step 2：选择数据集维度综合评测

目标：

在 Dataset Version 页面增加或复用：

**「数据集综合质量评测」**

注意：

现有单指标评测入口必须保留，不要将其重构为综合评测。

综合评测是数据集维度的新编排入口，能够一次关联多个指标。

用户点击后进入 Agent 推荐流程。

**闭环验收：**

点击入口后，系统能够识别当前 Dataset Version，并启动一次明确的综合评测配置会话。

### Step 3：Agent 自动推荐评测方案

目标：

Agent 根据当前数据集的画像、字段结构、数据类型及指标注册情况，推荐适用的质量指标和计算实现。

本阶段不强制使用 LLM。

优先评估两种方案：

**方案 A：确定性规则推荐**

基于：

- 数据集类型
- 字段映射
- Dataset Profile
- 指标适用条件
- Calculator 输入要求
- 算子可用状态

生成推荐方案。

**方案 B：轻量级 Planner 推荐**

参考项目已有论文中的 Logical Plan / Physical Plan 思想，将：

数据集特征 → 指标需求 → 算子能力 → 推荐执行方案

构建为轻量级规划逻辑。

不要求今天实现完整论文架构。

请比较两种方案的成本，并推荐今天可落地的实现。

推荐结果必须至少包括：

- 推荐评测维度
- 指标列表
- 指标适用原因
- 对应 Calculator
- 计算参数
- 当前是否可执行
- 未实现指标及原因
- 预期计算成本或复杂度（可以使用简单等级）

**闭环验收：**

前端展示 Agent 推荐结果，用户可以查看、接受或调整推荐内容。

不能仅在聊天框输出固定文字，推荐内容必须形成可被后续质量契约消费的结构化数据。

**人工审核**：不仅要考虑实现的难易程度，还要考虑可原来开发规划（docs/development/dataset-comprehensive-evaluation-plan.md）是否符合

### Step 4：Agent 自动构建多指标 Quality Contract

用户接受推荐后，Agent 自动生成综合质量契约草案。

契约应包含：

- dataset_version_id
- contract_id / version
- 指标及其定义版本
- Calculator Implementation 引用
- Calculator 参数
- 指标适用性
- 指标权重
- 质量判定规则
- 阈值
- 未实现指标处理策略

特别注意：

**一个综合质量契约必须支持多个 Metric Definition，而不是创建多个互不关联的单指标契约冒充综合评测。**

需要审查现有 Quality Contract 模型是否支持这一点。

如果不支持，请提出最小兼容扩展方案，保留原单指标流程。

契约生成后必须由用户确认，不能自动跳过确认步骤。

**闭环验收：**

用户能够在前端查看综合契约草案、确认配置，并将确认后的契约持久化。

**人工审核**：某个版本数据集已经生成过的质量契约记录应该保存在当前agent对话窗口文件系统内或者当前窗口的文件系统内。因为整个流程都可以在所选数据集的所选版本窗口内完成的。

### Step 5：提交评测任务

用户确认契约后，Agent 调用系统已有评测 API 提交任务。

这里需要评估：

- 是否需要 Logical Evaluation Plan
- 是否需要 Physical Evaluation Plan
- 是否已有 DAG / Stage Run 机制
- 当前后台任务执行方式
- 如何支持多指标任务执行
- 如何追踪单个指标状态

今天允许使用最小执行规划器：

Quality Contract → 指标执行列表 → Calculator 调度 → 结果汇总

但必须保留未来扩展 Logical / Physical Plan 的边界。

Agent 不直接执行指标算法，只负责流程编排与调用平台 API。

系统必须生成真实的 Evaluation Run，并保存执行状态。

**闭环验收：**

前端提交后能看到 Run ID、执行状态及进度。

任务必须真实进入后端执行流程，不允许使用纯前端模拟成功。

**人工评审**：只是有前端提交后的runId先阶段就能满足，开发计划中本来就包含Logical / Physical Plan，如果Logical / Physical Plan不影响agent推荐的实现，也可以先跳过这一步

### Step 6：执行指南数据质量全维度评测

本阶段采用分层实现。

**P0：真实计算指标**

优先复用现有 Calculator，例如：

- 重复度
- 缺失值或完整性
- 字段格式规范性
- 基础内容统计
- 其他当前已具备计算条件的指南指标

实际计算哪些指标必须由代码审查确定。

**P1：低成本可新增指标**

对可以通过 SQL、Pandas 或简单规则计算的指标，评估今天是否可以补充。

**P2：复杂指标占位**

例如：

- 需要 LLM 语义判断的指标
- 需要外部文本安全模型的指标
- 需要复杂语义相似度算法的指标
- 缺少标签或外部参考数据的指标

允许暂不实现，但必须保留对应 Metric Result 记录或状态，保证报告能够展示全维度覆盖情况。

必须严格区分：

- `SUCCESS`
- `FAILED`
- `SKIPPED`
- `NOT_IMPLEMENTED`
- `NOT_APPLICABLE`

如已有其他状态枚举，请基于现有模型合理映射。

**严禁为未实现指标生成虚假的评分、异常数量或计算证据。**

**闭环验收：**

一次综合评测可以产生多个指标结果，每个指标均有明确状态；已实现指标具备真实分数和计算证据。

**人工评审**：目前已经实现所有文本质量评估指标的占位

### Step 7：生成综合质量评测报告

这是本次 Demo 的核心展示成果。

报告必须包含：

1. 数据集基本信息与版本
2. 本次评测任务信息
3. 指南指标覆盖情况
4. 各维度评测结果
5. 综合质量评分
6. 指标明细
7. 异常样本或统计证据
8. 质量问题清单
9. 数据整改建议
10. 未评测指标及原因
11. 评测方法与局限性

前端优先使用：

- 综合评分卡片
- 各维度雷达图
- 指标结果明细表
- 异常问题列表
- 整改建议区域

综合评分必须采用透明、可解释的计算规则。

需要明确：

- 权重如何继承指南
- 未实现指标是否排除评分
- 不适用指标如何处理
- 部分指标失败如何处理
- 有效评测覆盖率如何计算

**禁止将已计算指标的加权平均分直接宣传为全指标综合质量得分。**

可以同时展示：

- 已评测指标加权得分
- 有效评测覆盖率
- 未完成评测指标数量

若指标层级存在父子关系，需要明确聚合规则，避免重复计权。

**闭环验收：**

评测完成后，前端能展示真实生成的综合报告，能够从综合维度下钻到具体指标和异常证据。

**人工评审**：本次一定要生成雷达图

### Step 8：Agent 推送结果与整改建议

当 Evaluation Run 完成后，Agent 自动推送结果。

推送内容至少包括：

- 评测完成通知
- 数据集及版本
- 综合评测结果摘要
- 质量薄弱维度
- 主要异常问题
- 优先整改建议
- 查看完整报告入口

整改建议必须尽可能基于真实 Metric Result 和 Quality Issue 生成。

今天可以先使用规则模板生成建议，不强制使用 LLM。

需要评估当前系统是否具备：

- 任务状态轮询
- 后台事件通知
- SSE / WebSocket
- Agent 会话状态持久化

优先选择今天能实现的最简单可靠方式。

**闭环验收：**

用户不需要手动重新发起提问，在任务完成后能在当前界面收到评测结果通知，并打开报告。

如果刷新页面，需要说明如何恢复 Run 状态和结果。

## 四、架构约束

### 4.1 保留现有单指标评测能力

系统需要同时支持：

- 单指标快速评测
- 数据集维度综合评测

两者共享 Metric Definition、Calculator Implementation、Metric Result 等底层能力。

不要破坏现有单指标流程。

### 4.2 Agent 与平台职责分离

Agent 负责：

- 推荐指标
- 生成契约草案
- 引导用户确认
- 调用任务提交 API
- 获取任务状态
- 解释结果与提出建议

平台负责：

- 数据接入与画像
- 指标注册
- Calculator 执行
- 任务调度
- 结果持久化
- 规则判定
- 报告生成

不要把计算逻辑写进 Agent Prompt 或 Skill。

### 4.3 避免过度架构设计

今天不要求：

- 完整多 Agent 框架
- 通用 Workflow Engine
- 完整复杂 DAG 调度器
- 所有指标的算法实现
- 全量 LLM 评测体系
- 说明文档评测
- 大规模分布式任务执行

但设计时要说明未来如何扩展，不得制造明显的架构死角。

### 4.4 真实 Demo 与占位能力严格区分

前端可展示尚未实现的指标，但必须明确状态。

不得使用假数据冒充真实结果。

不得在没有执行后台任务的情况下直接展示“评测完成”。

所有实际评分应能追溯到：

Dataset Version → Contract → Run → Calculator → Metric Result。
