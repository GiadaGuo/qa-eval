## 二、已确认的架构决策

### 决策 1：一个 Calculator，单样本多 Flag

实现一个：

`policy_structure_compliance@1.0.0`

对单条 SampleRecord：

1. 读取 HTML/plain/title 等输入。
2. 执行一次 HTML Block Extractor。
3. 选择结构解析模式。
4. 构建一次 StructureParseResult。
5. 基于共享中间结果执行四项检测。
6. 输出四组独立 Flag、数值和 Evidence。

四组 Flag：

- `parsing_success`
- `numbering_valid`
- `segmentation_correct`
- `path_locatable`

**一个 Calculator 可以输出多个指标，不需要为了每个 Flag 创建一个 Calculator。**

不要新增确定性共享计算平台、跨 Calculator 共享 Stage 或额外 DAG 编排能力。

### 决策 2：一个 MetricResult，多 observations

接受现有平台支持的：

**一个 Calculator → 一个 MetricResult → 多个 observation/measurement + 逐样本 evidence。**

暂不实现四个独立 MetricResult。

要求：

- 每个 measurement 有唯一且稳定的语义。
- 每个 Flag 具有独立的统计分母。
- MetricResult 总体 population 不能冒充各 Flag 的分母。
- 四组 Flag 的状态计数必须分别闭合。
- Evidence 保留样本级 Flag 和诊断信息。

不要为此大规模修改 MetricResult、Planner 或 Runner。

### 决策 3：保留现有 0204@1.0.0

现有 `0204@1.0.0` 用于字段缺失完整性，不允许覆盖或改变其原有语义。

请审计现有指标编码和父子指标注册规则，在 0204 体系下新增政策结构专项子指标。

要求：

- 不覆盖既有 Metric Definition。
- 不修改已有质量契约的语义。
- 不影响现有评测任务。
- 新增子指标承载 BG-02-03、BG-02-04、BG-02-05。
- 保持三个检测项与四组 Flag 的映射。
- 不重复实现 BG-02-03 和 BG-02-05 共同涉及的切分正确率。

如果现有编码体系无法安全新增子指标，先报告可行编码与兼容方案，不要自行修改旧指标。

### 决策 4：文种作为弱先验

Phase B 已确认，真实数据中存在：

- LEGAL
- OUTLINE
- GENERIC
- MIXED

因此：

- 不将文种代理分类作为 Ground Truth。
- 优先使用现有可信文种元数据。
- 缺少可信文种时，根据标题与正文结构推断。
- 文种与解析模式分开。
- 正文结构证据优先于标题关键词。
- 保留 document_type_source、confidence、mode_candidates 等诊断信息。

不新增数据库字段作为本次实施前提。

### 决策 5：Ground Truth 先实现接口

当前没有确认可用的人工结构标注集。

第一版要求：

- 定义版本化 Ground Truth Schema。
- 支持通过 Sample ID、Content ID、Dataset Version、标注任务版本关联标注。
- 支持 FINAL 状态的人工或导入标注。
- 实现预测结构与标注结构的对齐和判定逻辑。
- 使用小规模人工测试 fixture 验证 PASS/FAIL。
- 无有效标注时返回 UNAVAILABLE。

不要为了得到切分正确率而生成伪标注，也不要将解析成功率当作切分正确率。

### 决策 6：HTML 超长与 Evidence 策略

- `max_html_length_chars` 必须可配置。
- 初始默认值由真实数据长度分布和性能基准确定，不硬编码未经验证的经验阈值。
- 超长默认不静默截断，返回明确的 UNAVAILABLE reason。
- 可支持显式 FULL_SCAN 配置，但需测试资源开销。
- Evidence 默认不包含正文全文。
- 可保留短 excerpt，但必须限制长度、进行必要脱敏并记录策略。
- Evidence cap 不得改变聚合结果。

## 三、Phase D：实现

### D1. Schema、指标与结果协议

先冻结：

- 新增子指标的身份和版本。
- 四组 Flag 的状态模型。
- Observation/Measurement Schema。
- StructureParseResult Schema。
- Evidence Schema。
- Reason Code 与 Violation Code。

每组 Flag 支持：

`PASS / FAIL / NOT_APPLICABLE / UNAVAILABLE`

如现有平台使用不同状态枚举，应通过最小兼容映射实现，不随意修改全局状态模型。

聚合公式：

- `parsing_success_rate = parsing_pass / (parsing_pass + parsing_fail)`
- `numbering_compliance_rate = numbering_pass / (numbering_pass + numbering_fail)`（可选辅助指标）
- `numbering_defect_count = sum(sample_numbering_defect_count)`
- `segmentation_correct_rate = segmentation_pass / (segmentation_pass + segmentation_fail)`
- `path_locatable_rate = path_pass / (path_pass + path_fail)`

所有比率均应提供 numerator、denominator、四状态计数及可判定覆盖率。

分母为零时返回 UNAVAILABLE，不输出虚假的 0% 或 100%。

### D2. HTML Source-map

按照设计文档实现 lexical source-map。

要求：

- 原始 HTML 使用 Unicode code-point offset。
- normalized text 使用独立坐标。
- 保留 raw spans、DOM path 和块级边界。
- 支持 Entity、嵌套标签、跨标签编号、重复文本。
- 不从 plain 文本反推 HTML offset。
- 不通过不可靠的全局 str.find 伪造坐标。
- EXACT 必须支持 round-trip 验证。
- BLOCK_ONLY 必须能可靠定位到 HTML 块。
- UNAVAILABLE 必须附带原因。

跨标签节点应保留多个 raw spans，不能将 bounding range 误当成连续原文。

### D3. 结构解析

实现：

- LegalClauseParser
- OutlineParser
- GenericDocumentParser
- Mixed subtree 组合逻辑

支持：

- 章、节、条、款、项。
- 一、（一）、1.、（1）。
- 无章但有条的办法。
- 通知嵌入法条。
- 无编号普通通知。
- 批复型和纲要型规划。
- 其他通用政策文档。

结构解析应结合 HTML 块边界、编号形式、父子关系和上下文。

不要只依赖全文正则。

需要保留未解析候选、解析诊断及不支持的结构模式。

### D4. 四组 Flag 的具体判定

#### 1. parsing_success

判断样本是否成功完成适用结构模式下的解析。

PASS：

- 结构候选得到合理解析。
- 层级关系有效。
- 结构边界有效。
- 满足版本化解析覆盖标准。

FAIL：

- 有足够证据表明原文存在结构冲突，或明确违反适用结构规则。

UNAVAILABLE：

- 解析器不支持该合法结构。
- 解析能力不足。
- 缺少必要正文。
- 超长拒绝或运行异常。

不能仅因解析器未识别某种格式就判源文档 FAIL。

保留解析器诊断，避免将工具能力与源数据质量混淆。

#### 2. numbering_valid

基于解析树检查：

- 跳号。
- 重号。
- 倒序。
- 起始编号异常。
- 编号作用域与重置异常。

同一编号 transition 只计一个主要缺陷事件。

例如 `第一条 → 第四条`：

- GAP 事件数为 1。
- 缺失序号可以记录为 `[2, 3]`。
- 不得把跳号和缺号重复计入总缺陷数。

输出：

- numbering_valid。
- numbering_defect_count。
- skipped_number_count。
- duplicate_number_count。
- missing_number_count（明确其为缺失序号数还是事件数）。

对不需要编号的正常文档返回 NOT_APPLICABLE。

#### 3. segmentation_correct

基于独立人工标注判断。

- 无有效标注：UNAVAILABLE。
- 有有效标注：比较预测节点边界、类型和层级关系。
- 样本级 PASS 标准由版本化规则明确。
- 保存必要的 TP/FP/FN 或边界差异诊断。

不得用解析成功替代切分正确。

#### 4. path_locatable

验证：

- Content ID。
- DOM path。
- raw spans。
- offset 范围。
- span 顺序。
- 原文回溯。
- 必要节点定位覆盖情况。

本次约定：

- EXACT：满足验证条件时可判 PASS。
- BLOCK_ONLY：如果能够可靠定位到原始 HTML 块，也允许 PASS。
- UNAVAILABLE：无法可靠定位。
- FAIL：有可用坐标但经验证错误。

额外输出 `exact_location_rate` 作为诊断性 observation，用于衡量精确字符级定位覆盖程度。

注意区分样本级 path_locatable 与节点级 exact_location_rate，不能混用统计分母。

### D5. 样本级 Evidence

每条样本输出四组 Flag 的状态及必要诊断。

对异常保留：

- sample_id。
- content_id。
- check_item_id。
- flag。
- status。
- reason_code。
- violation_code。
- node_path。
- source_location。
- observed/expected。
- parser_version。

证据采用流式写入。

不要重复保存全文 HTML。

### D6. 平台集成

接入现有：

- Calculator Registry。
- Metric Definition。
- Binding。
- Logical/Physical Plan。
- Metric Result。
- Evidence Artifact。
- Rule/Report 消费链路。

必须验证多 observation 是否能够正确通过平台的 Schema 校验、结果持久化与报告生成。

## 四、Phase E：测试与验证

### E1. 单元测试

覆盖设计文档中的全部主要场景，包括：

- 标准法条。
- 无章办法。
- 通知大纲。
- 通知嵌入法条。
- 无编号通知。
- 规划。
- 混合模式。
- 未知文种。
- HTML 嵌套与跨标签编号。
- HTML Entity。
- 重复文本。
- 编号跳号、重号、倒序。
- 不同作用域的编号重置。
- 条款引用误匹配。
- 无标注与有标注。
- EXACT/BLOCK_ONLY/UNAVAILABLE。
- 超长 HTML。
- 单样本多 Flag。
- 聚合分母闭合。
- Evidence cap 不影响统计。
- 单样本异常隔离。

### E2. 集成测试

验证完整链路：

Dataset Version → Contract → Logical Plan → Physical Plan → Evaluation Run → Metric Result → Evidence。

重点验证：

- 新指标能够注册并绑定。
- 一个 Calculator 能产生多个 observation。
- 每个 observation 的分母正确。
- Evidence 可追溯到样本。
- 旧 0204 指标行为保持不变。
- 报告和规则层不会把 UNAVAILABLE 当成 FAIL。

### E3. 真实数据验证

优先使用 Phase B 固定抽样样本。

对不同文种、解析模式及异常类型进行人工复核，记录：

- 解析成功状态分布。
- 编号缺陷事件分布。
- 路径定位状态与精度分布。
- 无标注比例。
- UNAVAILABLE 原因。
- 典型误报和漏报。

特别检查：

- 无编号通知不会被误判为编号异常。
- 正文引用“第X条”不会被识别为新条款。
- 通知中嵌入办法时能够切换结构模式。
- HTML 坐标确实能够回溯原文。
- 不支持的合法结构不会被误判为质量缺陷。

只有人工核验过的样本才能用于报告 precision、recall 等准确性指标。

### E4. 性能测试

测量：

- 不同 HTML 长度下的处理耗时。
- 峰值内存。
- 每秒处理样本数。
- Evidence 大小。
- 预计全量执行时间。

全量数据约 321,902 条、8GB。

先执行抽样性能测试，再评估全量运行成本。

不要未经确认直接启动高成本全量评测。

### E5. 回归测试

执行相关单元、集成和 Registry/Planner 回归测试。

不得通过删除断言、降低校验标准或跳过失败测试来获得绿色结果。
