## 一、业务背景与核心原则

0204 包含三个检测项：

| 检测项   | 检测内容                         | 目标输出                   |
| -------- | -------------------------------- | -------------------------- |
| BG-02-03 | 按文种解析条款层级，保留原文坐标 | 条款解析成功率、切分正确率 |
| BG-02-04 | 多级编号连续性校验               | 编号连续缺陷数             |
| BG-02-05 | 条款切分与路径定位质量           | 切分正确率、路径可定位率   |

### 1. Calculator 的本质是样本级打标

一个 Calculator 可以对同一条 SampleRecord 输出多个独立 Flag 和数值。

例如：

```json
{
  "sample_id": "policy-001",
  "flags": {
    "parsing_success": "PASS",
    "numbering_valid": "FAIL",
    "segmentation_correct": "UNAVAILABLE",
    "path_locatable": "PASS"
  },
  "measurements": {
    "numbering_defect_count": 1
  }
}
```

数据集级再聚合：

- 条款解析成功率 = parsing_success 的 PASS 数 / 适用且可判定样本数。
- 编号连续缺陷数 = numbering_defect_count 求和。
- 切分正确率 = segmentation_correct 的 PASS 数 / 有有效标注且可判定样本数。
- 路径可定位率 = path_locatable 的 PASS 数 / 适用且可判定样本数。

**Calculator 数量不等于检测项数量，也不等于输出指标数量。**

是否合并 Calculator，应依据计算方法和中间产物是否共享。

初步推荐：

- 一个 `policy_structure_compliance` Calculator。
- 内部一次解析 SampleRecord。
- 共享 HTML Block、StructureParseResult、编号序列和坐标。
- 输出四组独立 Flag。

请审计现有框架，验证这个设计是否可行。

### 2. 四种判定状态

必须区分：

- PASS：达到判定标准。
- FAIL：明确未达到判定标准。
- NOT_APPLICABLE：不适用。
- UNAVAILABLE：缺少数据、人工标注或解析能力，无法判定。

尤其注意：

- 没有人工标注，不得声称切分正确。
- 没有编号，不一定是编号缺陷。
- 解析器不支持某种合法结构，不等于原文结构不完整。
- 一个 Flag 无法判定，不应阻止其他 Flag 正常输出。

## 四、Phase B：真实政策数据审计

请先定位可访问的 SampleRecord JSONL/Parquet 或项目已有样本。

如果真实数据不可访问，明确报告，不得伪造结果。

### B1. 可复现抽样

编写独立脚本，对以下类别分层抽样：

- 通知。
- 办法。
- 条例。
- 规划。
- 其他文种。
- 无编号正文。
- HTML 结构异常。
- 仅 PDF/图片/链接的正文。
- 通知中嵌入法条的正文。

要求：

- 固定随机种子。
- 记录样本 ID。
- 不加载全量 8GB 数据到内存。
- 不修改原始数据。
- 支持配置抽样规模。
- 输出可复现的统计文件。

### B2. HTML 结构分析

统计：

- p/div/span/br/table 等标签分布。
- HTML 段落边界是否可靠。
- 多层嵌套和跨标签编号。
- HTML Entity 和空白归一化。
- 重复标题、文号、目录、落款、附件。
- 只有图片或 PDF 链接的情况。

### B3. 编号模式分析

识别并统计候选模式：

法条体例：

- 第一章 / 第1章。
- 第一节 / 第1节。
- 第一条 / 第1条。
- 第X款。
- （一） / (一)。
- 1. / 1、 / （1）。

行政公文大纲：

- 一、二、三。
- （一）（二）。
- 1. 2. 
- （1）（2）。

注意排除正文引用、日期、金额、文件编号和附件编号。

正则命中率不能直接视为解析准确率。

### B4. 文种与结构模式

评估以下三种解析模式：

1. LEGAL_HIERARCHY：法条结构。
2. OUTLINE_HIERARCHY：行政公文大纲。
3. GENERIC_DOCUMENT：无显式编号的通用文档。

重点分析：

- 通知中是否存在完整法条。
- 办法是否存在无章但有条的情况。
- 规划是否存在批复型与纲要型。
- 是否需要同一文档中混合使用不同解析模式。
- 不同模式的适用边界与误判风险。

输出分层统计、典型样例 ID 和异常案例。

## 五、Phase C：技术设计

根据 Phase A/B 的真实结论设计实现方案。

### C1. Calculator 架构

优先评估：

`policy_structure_compliance`

内部建议包含：

- HtmlBlockExtractor
- StructureModeSelector
- LegalClauseParser
- OutlineParser
- GenericDocumentParser
- NumberingValidator
- SegmentationValidator
- PathLocalizationValidator

如果认为应拆分 Calculator，必须解释哪些模块无法共享计算方法或中间产物，以及拆分后的成本和收益。

### C2. HTML 原文坐标

HTML 是主要输入，纯文本为辅助和降级输入。

设计双坐标体系：

- normalized_text_start/end。
- source_html_start/end。
- dom_path。
- coordinate_status：EXACT / BLOCK_ONLY / UNAVAILABLE。

必须解决或明确限制：

- HTML 标签删除导致的坐标漂移。
- HTML Entity 解码。
- 重复文本。
- 跨标签文本。
- 嵌套 DOM。
- 空白归一化。
- 字符 offset 与字节 offset 的区别。

不能假设 BeautifulSoup/lxml 自动提供精确原始字符坐标。

需要给出可实现的 source-map 方案、复杂度和降级策略。

### C3. 结构解析结果 Schema

设计共享的 StructureParseResult，包括：

- 文种与解析模式。
- 层级节点树。
- 节点类型和父子关系。
- 原始编号与数值编号。
- 编号作用域。
- 原文坐标。
- 未解析候选。
- 解析诊断。
- 解析器版本。

说明哪些字段是后续四组 Flag 必需的。

### C4. 四组 Flag 的判定口径

分别给出：

1. parsing_success。
2. numbering_valid。
3. segmentation_correct。
4. path_locatable。

每个 Flag 必须提供：

- 适用条件。
- PASS 条件。
- FAIL 条件。
- NOT_APPLICABLE 条件。
- UNAVAILABLE 条件。
- 所需中间产物。
- 证据结构。
- 数据集级聚合公式和分母。

其中：

- 解析成功不能简单等于提取到至少一个节点。
- 编号校验需要按层级及父节点作用域进行。
- 跳号与缺号不能重复计入缺陷总数。
- 切分正确性必须依赖独立标注。
- 路径可定位性必须实际验证坐标有效性。

### C5. 外部附件

评估 PDF、图片、外部链接场景。

本阶段不要实现网络下载。

建议未来通过 Dataset Version 的版本化 Artifact 提供附件解析结果，而不是在 Calculator 中动态下载。

### C6. 性能与集成

设计：

- 流式逐样本处理。
- HTML 解析复用。
- 中间结果生命周期。
- Evidence 流式写入。
- 超长 HTML 限制。
- 单样本异常隔离。
- Calculator 版本与配置 Fingerprint。
- Registry/Planner/Aggregator 最小集成方案。
