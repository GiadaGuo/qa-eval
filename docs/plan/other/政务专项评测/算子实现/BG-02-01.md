
# 任务：实现 BG-02-01 政务网页 HTML 格式规范性检测 Calculator

## 一、任务目标

在现有 qa-eval 数据质量评测平台中，实现一个独立的政务专用 HTML 格式规范性 Calculator。

基本信息：

- 检测项 ID：BG-02-01
- 所属规则：BG-02 文档结构规范性评测
- 归属指标：0201 格式规范性
- Calculator 名称：`government_html_format_compliance`
- 建议文件名：`government_html_format_compliance.py`

原始 BG-02-01 定义为：

> 检查字体字号异常、表格跨页断裂、页眉页脚残留等版式问题。

考虑到当前政务数据集主要保存网页 HTML 正文，而非原始 PDF/DOCX，本次将检测范围具体化为：

**对 SampleRecord 2.0 中 `article.body.html` 的 HTML 结构、字体字号、段落排版、表格结构及非正文残留进行规范性检测，识别可能影响政务政策网页正文展示的格式异常。**

本轮要求完成真实代码实现、Calculator 注册、测试和开发说明。

不要修改前端，不要重构现有评测主链路，不要实现 PDF/DOCX/OFD 版式检测。

## 三、输入数据与适用性

主要输入：

`sample_records.jsonl`

逐行读取归一化后的 SampleRecord 2.0。

默认选择满足以下条件的 ContentItem：

```text
modality = text
role = article.body.html
presence = PRESENT
payload.type = inline_text
payload.format = html
payload.text 为字符串
```

例如：

```json
{
  "sample_id": "policy-001",
  "contents": [
    {
      "content_id": "body-html",
      "role": "article.body.html",
      "modality": "text",
      "presence": "PRESENT",
      "attributes": {
        "source_paths": ["$.content"],
        "transform": "identity"
      },
      "payload": {
        "type": "inline_text",
        "format": "html",
        "text": "<p style=\"font-size:14px\"><span style=\"font-size:21px\">政策正文</span></p>"
      }
    }
  ]
}
```

要求：

- 默认只检查 `article.body.html`。
- 允许配置其他 HTML role。
- 非 HTML ContentItem 不参与计算。
- NULL、MISSING、EMPTY 不应判定为格式异常。
- 无适用 HTML 时返回现有平台支持的 N/A 或不可计算状态。
- 不重复扫描 `article.body.plain`。
- 不将 HTML 缺失直接视为格式不合规，缺失属于其他质量维度。

## 四、核心检测规则

第一版实现以下六类规则。

### 4.1 HTML 结构异常

建议违规码：

`HTML_STRUCTURE_ANOMALY`

检测：

- 明显不合理的标签嵌套。
- 异常闭合标签。
- HTML 解析器可报告的结构错误。
- 明显不合法的表格或段落容器结构。

注意：

HTML 解析器通常具有自动容错能力，不能因为它成功构造 DOM 就认定源 HTML 完全合法。

也不能将所有非标准 HTML 写法都判为违规。

要求区分：

- 确定性结构异常。
- 解析器修复的疑似异常。
- 合法但不推荐的 HTML 写法。

不要使用正则表达式直接解析完整 HTML 结构。

### 4.2 字体字号异常

建议违规码：

- `FONT_SIZE_OUTLIER`
- `FONT_FAMILY_INCONSISTENCY`

这是本算子的重点。

需要分析 HTML 中：

- `font-size`
- `font-family`
- 相关 HTML 字体标签
- 父子元素样式覆盖
- 同类正文块之间的样式差异

例如：

```html
<p style="font-size:14px">
  <span style="font-size:21px">正常正文</span>
</p>
```

不能仅因为父子字号不同就判定异常。

要求：

1. 识别正文文本块及其实际声明的样式。
2. 考虑基本 CSS 继承和子元素覆盖。
3. 优先采用文档内主流样式作为比较基线。
4. 根据承载文本量判断样式是否属于正文主流。
5. 对明显偏离主流字号的局部文本给出疑似异常。
6. 标题、落款、日期、链接等特殊区域应适当降低误报。
7. 不将字体混用本身直接认定为违规。
8. 字号阈值和异常比例应可配置。

不要求第一版实现完整 CSS Cascade 或浏览器计算样式。

对于外部 CSS、复杂选择器、媒体查询等无法确定的情况，应明确标记检测能力受限。

**不要把 HTML 的样式声明误称为浏览器最终渲染样式。**

### 4.3 段落排版异常

建议违规码：

`PARAGRAPH_SPACING_ANOMALY`

检测：

- 明显异常的行高。
- 异常大的段落缩进。
- 极端段前段后间距。
- 不合理的负边距。
- 可能影响正文阅读的异常对齐方式。

注意：

- 正常的 `text-align: justify` 不应报错。
- 正常落款右对齐不应报错。
- 政务正文常见的首行缩进不应报错。
- 不能仅因为 `line-height:39px` 就判定异常。
- 对 CSS 单位必须正确解析，不允许直接比较不同单位的数值。

建议第一版重点检测明显极端的异常值，对无法换算的单位返回未知或跳过该项。

### 4.4 连续空白块异常

建议违规码：

`EXCESSIVE_EMPTY_BLOCKS`

检测：

- 连续大量空 `<p>`。
- 连续大量 `<br>`。
- 仅包含空白字符或 `&nbsp;` 的连续块。
- 明显影响阅读的冗余空白结构。

要求：

- 单个空段落不报错。
- 正常落款前的留白不报错。
- 正常 `&nbsp;` 不报错。
- 使用可配置的连续数量阈值。
- 对 HTML Entity 正确解码后再判断可见内容。
- 不把合法的表格占位或必要排版留白全部视为异常。

### 4.5 表格结构异常

建议违规码：

`TABLE_STRUCTURE_ANOMALY`

检测：

- 不合理的 `table / tr / td / th` 层级。
- 表格缺少有效行列。
- 明显异常的空表格。
- `rowspan`、`colspan` 非法取值。
- 可识别的行列结构冲突。

要求：

- 合法的合并单元格不应误报。
- 嵌套表格不应一律判异常。
- 简单表格和复杂表格应区分检测能力。
- 不能从 HTML 源码直接判定表格是否跨页断裂。

原始 BG-02-01 中的“表格跨页断裂”本版本明确不覆盖，因为 HTML 源码通常不包含可靠的物理分页信息。

### 4.6 非正文 HTML 残留

建议违规码：

`HTML_LAYOUT_RESIDUE`

重点检查 DOM 结构层面的非正文元素，例如：

- 明确的导航栏容器。
- 面包屑导航。
- 打印工具栏。
- 网站页脚。
- 返回顶部按钮。
- 明显的网页模板残留。

识别依据可以包括：

- 元素标签。
- class/id。
- ARIA role。
- 常见结构特征。

但不能仅凭 `footer`、`nav` 等单个标签就一律判定异常。

尤其要区分：

- 网站公共页脚。
- 政策正文中的合法落款、发布日期。
- 正文引用的合法链接。

已有 `text_purity` 中的文本型 `LAYOUT_RESIDUE` 规则不要直接复制。

本 Calculator 重点检测 HTML DOM 结构层面的残留。

## 五、规则配置与版本管理

不要把所有阈值直接硬编码在 Calculator 中。

建议采用统一规则配置，包括：

- 是否启用各类检测。
- 字号异常阈值。
- 主流字体判定比例。
- 连续空白块阈值。
- 行高及缩进异常阈值。
- HTML 残留特征规则。
- 表格检查开关。

区分：

1. 通用 HTML 格式规则。
2. 政务网页启发式规则。
3. 将来可接入的正式政务排版标准规则。

当前没有提供正式政务网页排版标准，因此**不能把启发式异常直接表述为违反国家标准或政务规范**。

规则应有版本号，并在结果中记录规则配置指纹。

## 六、证据输出设计

每条异常证据至少包含：

```json
{
  "sample_id": "policy-001",
  "content_id": "body-html",
  "role": "article.body.html",
  "source_paths": ["$.content"],
  "violation_code": "FONT_SIZE_OUTLIER",
  "severity": "WARNING",
  "dom_path": "p[3]/span[2]",
  "observed_value": "8px",
  "expected_value": "document_body_baseline",
  "message": "局部正文字号明显偏离文档主体字号",
  "evidence_text": "相关正文片段"
}
```

要求：

- 证据必须定位到 sample_id 和 content_id。
- 尽可能输出 DOM 路径。
- DOM 路径应基于真实解析树生成。
- 如能可靠定位源 HTML 字符区间，可以补充 offset。
- 如果解析器不支持源字符定位，不要伪造 offset。
- evidence_text 应限制长度。
- 不要将完整 HTML 正文写入日志。
- 同一异常可以保留多个定位信息，但不能无限重复输出。

## 七、统计指标与 Metric Result

遵循现有 Metric Result 契约。

建议主指标：

`compliant_record_ratio`

计算方式：

`compliant_record_ratio = 1 - affected_record_count / eligible_record_count`

其中：

- `eligible_record_count`：至少包含一个适用 HTML ContentItem 的记录数。
- `affected_record_count`：至少命中一项有效格式违规的记录数。

但必须区分：

- 确定性违规。
- 启发式疑似异常。
- 无法判定的情况。

请设计合理的默认合规口径，**不要把所有低置信疑似异常都直接计为不合规**。建议将启发式告警单独统计，只有符合明确判定规则的异常才进入主合规率；具体以现有 Metric Result 和 Calculator 约定为准。

诊断字段至少包括：

- `eligible_record_count`
- `scanned_content_count`
- `affected_record_count`
- `confirmed_violation_record_count`
- `suspected_anomaly_record_count`
- `violation_count`
- `violation_counts_by_code`
- `skipped_content_count`
- `semantic_coverage`
- `rule_version`

注意：

- 同一 SampleRecord 存在多条异常，记录级只计一次。
- 同一 HTML 内容中多个 DOM 节点可以分别产生证据。
- 无适用 HTML 时不能默认合规率 100%。
- 不在 Calculator 内计算最终质量评分。
- 不要修改现有 0201 通用 Calculator 的结果口径。

建议证据 Artifact：

`government-html-format-violations.jsonl`

## 十、测试要求

至少覆盖以下场景：

### 正常场景

1. 正常政务 HTML 正文通过。
2. 父级 `14px`、子级 `21px` 的合法样式覆盖不误报。
3. 正文统一使用仿宋字体不误报。
4. 合法标题、正文、落款使用不同字号不误报。
5. 正常 `text-align:justify` 不误报。
6. 正常落款右对齐不误报。
7. 正常 `&nbsp;` 和 `<br/>` 不误报。
8. 正常表格、合并单元格不误报。
9. 正文中的合法引用链接不误报。

### 异常场景

10. 明显异常的 HTML 标签嵌套。
11. 极小或极大的正文局部字号。
12. 同类正文中明显异常的字体混用。
13. 极端行高或缩进。
14. 连续大量空段落。
15. 非法 rowspan / colspan。
16. 明显的导航栏或网站页脚残留。
17. 同一记录多个异常只计一次 affected_record。

### 边界场景

18. 缺失 HTML。
19. 空 HTML。
20. 只有纯文本正文。
21. HTML 解析失败。
22. 超长 HTML。
23. 同一记录存在多个 HTML ContentItem。
24. HTML Entity 与 CSS 单位解析。
25. 无法确定最终样式时正确标记检测限制。
26. 异常证据 DOM 路径正确。
27. Calculator 可注册、可执行。
28. 现有 format_compliance、text_purity 相关测试不回归失败。

必须增加端到端集成测试，覆盖：

`Dataset Version → Calculator → Metric Result → Evidence Artifact`
