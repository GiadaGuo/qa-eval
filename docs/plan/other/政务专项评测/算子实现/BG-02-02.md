# 任务：实现 BG-02-02 文本编码合法性与乱码异常检测 Calculator

## 一、任务目标

在现有 qa-eval 数据质量评测平台中，新增独立 Calculator，用于实现政务数据集 BG-02-02 检测项。

**检测项信息：**

- 检测项 ID：BG-02-02
- 所属规则：BG-02 文档结构规范性评测
- 归属质量指标：0201 格式规范性
- 检测名称：文本编码合法性检查
- 原始规则：校验文本 UTF-8 编码合法性，识别乱码字符与非法字节序列

本次实现重点面向**归一化后的 SampleRecord 2.0 中的文本字段**，而不是原始 PDF/DOCX 等物理文件。

要求复用现有 Calculator 架构，完成真实可执行、可注册、可测试、可追溯的独立检测算子。

不要重写已有的 `format_compliance.py`，也不要破坏 `text_purity` 的现有功能。

## 二、首先审计现有项目

在编写代码前，必须阅读以下实现：

1. `format_compliance.py`：现有 0201 通用格式规范性 Calculator。
2. `text_purity.py` 及 `text_purity_rules.py`：现有乱码、异常字符检测规则。
3. Calculator 基类、注册表、参数 Schema、Metric Registry 和 Binding 机制。
4. `SampleRecordV2`、`ContentItem`、`payload` 等契约。
5. `LogicalPlannerService`、`PhysicalPlanner` 和 Calculator 执行器。
6. Metric Result、诊断信息、证据 Artifact 的生成及持久化机制。
7. 现有 Calculator 的单元测试、集成测试及测试 Fixture。

请先确认实际文件路径和现有接口，不要凭空创建一套新的执行框架。

## 四、Calculator 设计

建议名称：

`sample_text_encoding_compliance`

建议代码文件：

`sample_text_encoding_compliance.py`

但最终路径、类名和注册方式必须符合现有项目约定。

### 4.1 检测范围

默认检测：

- `modality = text`
- `presence = PRESENT`
- `payload.type = inline_text`
- `payload.text` 为字符串

支持通过参数配置：

- `include_roles`
- `exclude_roles`
- `include_content_ids`
- `check_replacement_character`
- `check_unicode_validity`
- `check_mojibake`
- `check_control_characters`
- `max_evidence_per_record`

参数必须有明确默认值、类型校验和文档说明。

建议默认扫描所有适用的文本 ContentItem，同时允许用户限定 `article.title`、`article.body.plain` 等角色。

对于 `presence = NULL / MISSING / EMPTY`，不要当作编码异常；应按既有契约区分不适用、跳过或空文本情况，并记录统计数量。

### 4.2 核心检测规则

#### A. Unicode 合法性

检测：

- 孤立 UTF-16 surrogate code point（U+D800 至 U+DFFF）。
- Unicode 文本中不应出现的非法或异常码位。
- 异常控制字符。

注意：

- 普通中文、英文、标点、Emoji 应正常通过。
- `\n`、`\r`、`\t` 等常见文本控制字符默认允许。
- 零宽字符、格式字符不能一律判定非法，应结合规则判断。
- 私用区字符和未分配码位可作为可配置的疑似异常，不能一律判为编码错误。
- Unicode 规范化差异不应直接判定为编码非法。

#### B. 替换字符

检测：

`U+FFFD`，即 `�`。

由于现有归一化读取器可能使用：

```python
decode("utf-8", errors="replace")
```

因此 U+FFFD 可能意味着上游存在非法字节，也可能是源数据原本包含该字符。

要求：

- 检测并记录 U+FFFD。
- 不直接断言原始 UTF-8 字节非法。
- 违规原因表述为“发现替换字符，疑似上游解码异常”。
- 输出字符位置、上下文及对应 ContentItem。

#### C. 常见乱码模式

复用现有 `text_purity_rules.py` 中可复用的规则，例如：

- Latin-1 mojibake 特征。
- `锟斤拷`。
- 其他已有乱码签名。

优先提取公共规则函数或复用现有检测接口。

避免复制正则表达式，形成两套不一致的规则库。

注意：

- 乱码规则可能存在误报。
- 需要区分确定性异常与疑似异常。
- 不要对所有非中文字符直接判异常。
- 不要将 HTML 标签、CSS 属性、合法 HTML Entity 误判为乱码。

#### D. HTML 文本处理

对于：

`payload.format = html`

必须考虑 HTML 标签、CSS、HTML Entity 对检测的影响。

例如：

```html
<p style="font-family: Calibri;">正文 内容</p>
```

这里的 `Calibri`、`font-family`、`&nbsp;` 都不是乱码。

建议：

- 保留原始 HTML 字符串。
- 对乱码特征检测优先使用可见文本。
- 不对 HTML 标签、属性、URL、CSS 样式做普通自然语言乱码判断。
- 对 U+FFFD、孤立代理项等 Unicode 层面的异常，可检查整个 HTML 字符串。
- 证据位置必须明确属于原始 HTML 还是提取后的可见文本。
- 如果无法可靠建立字符位置映射，不得伪造原始 HTML offset。

请评估是否复用现有 HTML 清洗工具，避免引入不必要的新依赖。

## 五、检测结果与违规码

建议定义独立违规码：

| 违规码                           | 含义            | 建议分类     |
| -------------------------------- | --------------- | ------------ |
| `INVALID_UNICODE_SURROGATE`    | 孤立代理项      | 确定性异常   |
| `REPLACEMENT_CHARACTER`        | U+FFFD 替换字符 | 疑似解码异常 |
| `SUSPICIOUS_MOJIBAKE`          | 疑似乱码片段    | 疑似异常     |
| `SUSPICIOUS_CONTROL_CHARACTER` | 异常控制字符    | 规则异常     |

如果现有规则库已有统一违规码，优先复用或建立映射。

每条违规证据至少包含：

```json
{
  "sample_id": "00000138a5514f2cb11648fc94495141",
  "content_id": "body-plain",
  "role": "article.body.plain",
  "source_paths": ["$.content"],
  "violation_code": "REPLACEMENT_CHARACTER",
  "severity": "WARNING",
  "start_offset": 120,
  "end_offset": 121,
  "matched_text": "�",
  "context": "前文...�...后文",
  "message": "检测到 Unicode 替换字符，疑似上游解码异常"
}
```

注意：

- offset 使用 Python Unicode 字符串的字符索引。
- 明确采用左闭右开区间。
- 不得将字符索引冒充为原始文件字节偏移。
- evidence 应控制上下文长度，避免输出整篇正文。
- 不要在日志中大量打印完整政策内容。

## 六、重复字段与统计口径

这是必须重点解决的问题。

同一条 SampleRecord 可能包含：

- `article.body.html`
- `article.body.plain`

两者可能都来自：

`$.content`

其中 plain 是由 HTML 派生得到的。

如果两个字段都检测到相同乱码，不能简单计为两条异常记录。

要求至少区分三个层级：

### 1. ContentItem 层级

统计：

- `scanned_content_count`
- `affected_content_count`
- `violation_count`

### 2. SampleRecord 层级

统计：

- `scanned_record_count`
- `affected_record_count`

同一个 sample_id 出现多条异常，`affected_record_count` 只增加一次。

### 3. 来源字段层级

利用：

- `attributes.source_paths`
- `attributes.transform`
- `content_id`

识别多个 ContentItem 是否来自同一个源字段。

设计合理的去重策略：

- 同一个 SampleRecord 的不同 ContentItem 证据仍可保留。
- 同一个 SampleRecord 的异常记录数只计算一次。
- 不同来源字段不应错误合并。
- HTML 与 plain 的字符 offset 不可直接比较。
- 如果无法确认两个异常是否为同一源位置，不要强行做事件级去重。

请明确各统计指标的分母和去重规则。

## 七、Metric Result 输出

要求符合现有平台 Metric Result 契约。

建议主指标：

`compliant_record_ratio`

定义为：

`1 - affected_record_count / eligible_record_count`

其中 `eligible_record_count` 为至少存在一个符合检测条件的文本 ContentItem 的记录数。

同时输出诊断信息：

- `eligible_record_count`
- `scanned_content_count`
- `affected_record_count`
- `affected_content_count`
- `violation_count`
- `violation_counts_by_code`
- `skipped_content_count`
- `coverage`
- `semantic_coverage`

注意：

- 如果没有适用文本，不应默认返回合规率 100%。
- 应使用现有 Metric Result 契约支持的 N/A 或不可计算状态。
- 如果现有结果模型不支持这些字段，请通过已有 diagnostics / artifacts 等扩展点实现，不要擅自修改核心契约。
- 不要在 Calculator 内直接计算最终质量评分或雷达图分数。

建议证据 Artifact：

`sample-text-encoding-violations.jsonl`

每行一条可追溯异常。

### 关于覆盖范围的说明

`semantic_coverage` 必须明确：

**Covered：**

- SampleRecord 文本字段 Unicode 异常。
- 替换字符。
- 可识别的疑似乱码。
- 异常控制字符。

**Excluded：**

- 原始上传文件的 UTF-8 字节合法性。
- 原始非法字节精确位置。
- PDF/DOCX/OFD 物理文件编码。
- OCR 准确性。
- 所有语义层面的文本错误。

禁止将该 Calculator 描述为“已完成原始文件 UTF-8 字节合法性检测”。

## 九、性能与工程要求

当前数据集可能达到：

- 约 32 万条 SampleRecord。
- 归一化 JSONL 约 8 GB。
- 单条记录可能包含较长 HTML 正文。

因此要求：

- 流式逐行读取。
- 不得一次性加载全部 JSONL。
- 不得将全部异常证据保存在内存中。
- 证据逐条写入 Artifact。
- 正则表达式尽量预编译。
- 避免对每条记录重复初始化 HTML Parser。
- 支持异常数量和证据数量上限。
- 对超长文本给出明确的扫描策略，不能静默跳过后声称全量覆盖。
- 尽量复用现有 ArtifactStore、Calculator ExecutionContext 和 Result Writer。

对于大规模数据，内存使用应基本不随记录总数线性增长。

## 十、测试要求

至少覆盖以下场景：

1. 正常中文政策标题通过。
2. 正常 HTML 正文通过。
3. 正常纯文本正文通过。

8. 普通英文、数字、Emoji 不误报。

10. 异常控制字符被检测。
11. `presence = MISSING` 正确跳过。
12. 非文本模态正确跳过。
13. 同一记录 HTML/plain 均异常时，affected_record_count 只计一次。
14. 同一来源字段不同 ContentItem 保留独立证据。
15. 无适用文本时正确返回不可计算状态。
16. 证据 offset 与实际字符串位置一致。
17. 不同 include_roles 配置生效。
18. 大量记录流式处理不出现明显内存线性增长。
