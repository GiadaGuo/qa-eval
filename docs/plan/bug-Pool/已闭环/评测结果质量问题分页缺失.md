# 评测结果质量问题分页缺失

## 现象

评测结果详情页 Quality Issues 一次请求并展示最多 100 条质量问题
(`GET /api/v1/evaluation-runs/{run_id}/quality-issues?limit=100`),无分页组件:

- 数据多时需大量滚动(真实环境单 Run 有 7562 条质量问题)。
- 超过 100 条的记录用户无法查看。
- 后端 `list_issues()` 为"全量查询 + Python 切片":每次请求把该 Run 的全部
  issue 行载入内存再 `rows[offset:offset+limit]` 切片,随数据量线性恶化。

## 根因

- 后端路由本身已支持 `limit + offset`(≤100)且响应含
  `total/limit/offset/issues`,契约可完全复用,不需要改响应结构。
- 但 `QualityResultService.list_issues` 没有下推 LIMIT/OFFSET 到数据库,也没
  有独立的 count 查询,不满足后端分页要求。
- 前端 `getQualityIssues` 硬编码 `limit=100` 且不带 offset;页面无分页状态与
  分页组件。

## 排查中发现的额外隐患(未在本次修复)

模型的 `postgresql.UUID(as_uuid=True)` 在 SQLite 测试库上 DDL 渲染为裸
`UUID` 类型,按 SQLite 亲和性规则落到 NUMERIC:hex 全为数字的 UUID(如
`UUID(int=1)`)会被无损转成 INTEGER 存储,读回时 `uuid.UUID(int)` 崩溃
(`'int' object has no attribute 'replace'`)。`uuid4()` 几乎必含 a–f 字母
所以平时无感;生产 PostgreSQL 不受影响。测试已用含字母的递增 UUID 规避
(`_sequential_issue_uuid`,跨 Run 复用同一内存库时加 per-run 基址避免主键
冲突)。
