`http://localhost:5173/api/v1/document-report-tasks/01a1857b-57a8-7240-8281-455bbe961959`

`01a1857b-57a8-7240-8281-455bbe961959`

5. 检查前端轮询该接口的代码：

   - 是否正确解析 response.status。

### 关键要求

请先输出该 Task 的实际状态、关联 Run 和 Report 的真实情况，并定位导致持续轮询的具体原因，然后直接进行修复。

如果该 Task 已无法恢复，不要伪造成功状态。应先修复根因，再使用真实说明文档创建一个新的 Report Task 完成验证。

最终必须提供：

- 原 Task ID 的故障原因。
- 修改的代码文件和行号。
- 新 Task ID（如重新执行）。
- 修复后任务最终状态。
- 是否成功生成真实报告。
- 前端是否正确停止轮询。

不要只通过增加轮询超时解决问题，必须同时修复造成任务无法完成或报告无法展示的实际原因。

## 一、问题背景

当前项目：`qa-eval` 数据质量评测平台。

目前在**说明文档评测模块**中，用户点击“生成报告”后，前端持续轮询，但报告始终无法生成或展示。

需要排查并修复完整链路，而不是仅修改前端轮询行为。

注意：

- 说明文档评测与数据集综合评测是两个不同的业务入口。
- 应优先复用已有的 Evaluation Run、Metric Result、Quality Report 等平台能力。
- 但不能因为数据集评测链路正常，就假设说明文档评测也正常。
- 不要为了修复问题破坏已经正常运行的数据集综合评测流程。

## 二、任务目标

1. 定位导致报告持续轮询的真实根因。
2. 修复前后端相关问题。
3. 保证说明文档评测能够正常生成并展示报告。
4. 保证失败时能正确终止轮询并显示错误原因。
5. 增加必要的测试，避免问题再次出现。
6. 保持现有系统架构和接口兼容性。

## 三、第一阶段：梳理完整调用链

先检查项目实际代码，不要根据文件名猜测实现。

从前端“生成报告”按钮开始，沿调用链逐层追踪：

### 1. 前端入口

定位：

- 说明文档评测页面组件
- 生成报告按钮对应的 onClick
- API Client
- 轮询 Hook 或定时器
- 状态管理
- 报告展示组件

重点检查：

- 点击后调用哪个 API？
- 请求携带哪些参数？
- 是否正确传入 Document Version ID、Contract Version ID、Run ID？
- 是否存在重复创建 Run 的情况？
- 轮询使用的 ID 是否与创建任务返回的 ID 一致？
- 轮询停止条件是什么？
- 是否只判断 SUCCEEDED，而没有处理 FAILED、CANCELLED 等终态？
- 页面卸载或切换版本后是否清理定时器？
- 是否存在 stale closure、重复 useEffect、状态覆盖或无限重试？

### 2. 后端 API

定位说明文档评测相关的：

- 评测提交 API
- Run 查询 API
- Report 查询 API
- Report 生成 API

检查：

- API 返回的任务 ID 是否正确？
- 请求是否真正创建 Evaluation Run？
- 是否提交后台执行？
- 返回状态是否与前端枚举一致？
- 是否存在 HTTP 200 但业务状态失败的情况？
- 是否存在 404、409、422、500 被前端当成“仍在处理中”继续轮询的情况？

### 3. 后端执行链路

沿实际代码追踪：

Document Version → Document Profile / Content → Quality Contract → Evaluation Plan → Evaluation Run → Calculator → Metric Result → Rule Evaluation → Quality Report

以实际实现为准，不要假设所有阶段已经接入。

检查：

- Document Version 是否已发布且可读取？
- 是否存在文档内容提取失败？
- 是否正确绑定说明文档指标（例如 0101、0102、0103 等）？
- Calculator 是否已注册且可执行？
- 是否存在 Placeholder Calculator 被错误调度？
- 任务是否真正被 Worker 消费？
- 是否存在同步/异步任务未 await、事务未提交、异常被吞掉等问题？
- Run 是否从 PENDING 正常进入 RUNNING？
- Calculator 执行失败后是否正确进入 FAILED？
- 是否存在数据库状态一直停留在 RUNNING 的情况？

### 4. 报告生成与持久化

检查：

- 报告是在 Run SUCCEEDED 后自动生成，还是需要独立触发？
- Report Builder 是否支持 DOCUMENT 类型？
- 报告查询是否使用正确的 Document Version / Run ID？
- 是否存在 Run 已完成但 Report 记录没有创建？
- 是否存在报告 JSON 已生成但前端查询不到？
- 是否存在数据库事务、外键、Schema 或序列化问题？
- 是否存在报告生成异常但没有更新任务状态？

特别检查是否出现：

**Run 已 SUCCEEDED → Report 不存在 → 前端持续等待 Report。**

如果是这种情况，需要修复报告生成与查询的衔接，而不是让前端无限重试。

## 五、第三阶段：修复

按照实际定位的根因进行最小必要修改。

### A. 后端状态机

确保评测任务具备明确的状态流转：

PENDING → RUNNING → SUCCEEDED / FAILED / CANCELLED

如果实际状态机名称不同，以项目现有定义为准。

要求：

- 成功时正确提交结果。
- 失败时记录错误原因。
- 不允许捕获异常后继续保持 RUNNING。
- 避免任务永远停留在非终态。
- 对异常中断的任务提供合理的超时或恢复机制，但不要随意将耗时任务标记为失败。

### B. 报告生成

确保：

- 评测成功后能够生成对应报告。
- 报告与正确的 Document Version、Contract Version、Run 关联。
- 报告生成失败时能够返回明确错误。
- 重复查询不会重复生成报告。
- 重复点击生成按钮不会意外创建多个相同任务。
- 报告生成操作具有合理的幂等性。

如果 Report 是独立于 Evaluation Run 的异步任务，必须明确区分 Run 状态和 Report 状态，不能将 Run SUCCEEDED 直接视为 Report READY。

### C. 前端轮询

修复轮询逻辑，至少满足：

- PENDING / RUNNING：继续轮询。
- SUCCEEDED 且报告 READY：停止轮询并展示报告。
- FAILED / CANCELLED：立即停止并显示错误。
- Run SUCCEEDED 但报告仍在生成：根据报告任务状态继续等待。
- Run SUCCEEDED 但报告明确不存在且不会再生成：停止轮询并显示异常。
- 网络错误：有限次数重试，不能无限重试。
- 超时：停止轮询并提示用户刷新状态或重试。
- 组件卸载：取消轮询。
- 用户重新发起任务：旧轮询不得覆盖新任务结果。

**不要用简单的 setTimeout 或固定等待时间掩盖后端问题。**

### D. 用户体验

生成报告按钮应具有明确状态：

- 未开始：生成报告
- 提交中：正在提交
- 执行中：正在评测
- 报告生成中：正在生成报告
- 成功：查看报告
- 失败：显示原因并允许重试

不要求重新设计页面，只修复必要的状态反馈。
