
# UI 修复：将顶部历史对话卡片网格改为 Codex 风格纵向 List

项目：`qa-eval`

目标页面：数据集版本 → 数据集综合质量评测 → Agent 对话工作区。

## 一、明确需求

当前「历史对话（N）」区域位于 Agent 对话工作区顶部，展开后使用多列卡片网格显示会话。

当前存在的问题：

- 每条会话使用较大的 Card。
- 一行排列多个 Card。
- 会话增加后不断向下堆积。
- 重复展示会话创建时间和最近更新时间。
- 每条会话显示 ACTIVE、COMPLETED 等状态标签。
- 历史会话占据过多页面空间。

**目标是参考 Codex 的 Chats 会话记录，将卡片网格改成单列纵向 List。**

必须注意：

1. 保留「历史对话（N）」在页面顶部的原位置。
2. 保留原有折叠和展开能力。
3. 展开后每条会话独占一行，自上而下排列。
4. 不使用多列 Grid。
5. 不使用横向排列或横向滚动。
6. 不新增左侧 Sidebar。
7. 不改变下方 Agent 对话工作区布局。

## 三、会话条目样式

每条会话使用紧凑 Row：

- 左侧：会话标题。
- 右侧：最近更新时间的简短表示。
- 每条高度约 36～44px。
- 标题超长时省略。
- Hover 使用浅背景。
- 当前选中项使用细竖线或浅背景。
- 不显示完整的“最近更新：2026/10/29 ...”文字。
- 默认不显示 ACTIVE / COMPLETED 等大 Badge。
- 如确实需要状态，可用简短文字、Tooltip 或详情面板展示。

不要使用 Card、Shadow、大面积 Border。

视觉风格保持项目现有森系配色。

## 四、控制列表高度

这是本次必须解决的问题。

历史会话数量可能从 6 条增长到几十条甚至上百条。

不能因为历史会话不断增加而无限撑高页面。

要求：

- 历史对话容器设置合理的最大高度，例如 260～320px。
- 超过高度后仅列表内部纵向滚动。
- 顶部标题栏保持可见。
- 页面主体不被大量历史记录挤压。
- 折叠后只保留标题栏。
- 不出现横向滚动条。

如果当前 Session 列表已经支持分页或增量加载，保留现有机制；不要求一次加载全部历史数据。

## 五、会话标题

当前所有会话标题类似：

`新对话 · 2026/10/29 14:09:20`

本次优先保留现有标题逻辑，不强制开发 AI 自动命名。

但应确保：

- 标题紧凑展示。
- 创建时间不与更新时间重复显示。
- 后续如果存在用户自定义标题，可以直接显示。
- 不调用外部 LLM 生成标题。

## 六、保留原有交互

必须保留：

- 点击会话切换 Agent Session。
- 当前会话选中高亮。
- 创建新会话。
- 刷新历史会话。
- 按最近更新时间倒序。
- 不同 Dataset Version 的会话隔离。
- 历史消息恢复。
- Proposal Revision 恢复。
- Contract 和 Evaluation Run 状态恢复。
- 切换会话时异步请求隔离。

本次不修改后端 Session 业务逻辑。

## 九、新增历史会话删除功能（必须实现）

目前历史会话不支持删除，本次 UI 改造需要同时补齐完整的会话删除能力，包括前端交互、后端 API、数据库处理及测试。

### 9.1 前端交互

在每条纵向 List 会话右侧增加 `···` 操作菜单。

要求：

- 默认保持列表简洁，鼠标悬停或键盘聚焦时显示操作入口。
- 点击 `···` 展示「删除会话」。
- 点击删除后弹出二次确认框。
- 删除成功后立即更新会话列表和数量。
- 删除失败时显示中文错误信息。
- 删除过程中禁用重复提交。
- 支持键盘操作和触屏访问。

确认文案：

**删除这条历史对话？**

删除后将无法继续查看该会话的聊天记录和未发布草稿。已发布的质量契约、评测任务及报告不会受到影响。

按钮：

「取消」 / 「确认删除」

使用项目现有的 Ant Design 组件和森系主题，不引入新的 UI 框架。

### 9.2 后端删除 API

首先检查现有 Agent Session API 是否支持删除。

如果已有接口，优先复用。

如果没有，按照项目现有 REST API 规范增加类似：

`DELETE /api/v1/agent-sessions/{session_id}`

具体路径以现有路由为准。

必须验证：

- Session 是否存在。
- Session 是否属于当前 Dataset Version。
- 当前请求是否有权操作该 Session。
- Session 是否存在进行中的 Proposal 发布、Contract 创建或 Evaluation Run 提交操作。
- 是否存在仍在运行的后台 Agent 任务。

不能仅凭前端隐藏按钮实现删除。

### 9.3 删除语义与数据边界

明确区分：

**可以删除的会话数据**

- Agent Session。
- 该 Session 的聊天消息。
- 会话专属且未发布的 Proposal 草稿及 Revision（在确认无外部引用后）。
- 会话专属临时状态。

**必须保留的独立业务资产**

- Dataset Version。
- 已发布 Quality Contract。
- Evaluation Run。
- StageRun。
- Metric Result。
- Quality Issue。
- Quality Report。
- 其他被独立业务对象引用的数据。

先检查数据库外键及引用关系。

如果 Session 与已发布 Contract、Run 存在关联，应设计安全的解除关联、保留必要审计引用或软删除方案。

不得使用未经审查的 `ON DELETE CASCADE` 删除业务资产。

优先采用与现有数据模型兼容的软删除；如果现有架构更适合硬删除，必须先验证引用安全性和事务一致性。

### 9.4 正在执行的会话

如果 Session 正在执行 Agent 操作或关联活跃任务：

- 不允许删除操作造成孤儿任务。
- 不允许因为删除会话而中断独立的 Evaluation Run。
- 必须检查现有任务生命周期和会话引用关系。
- 如无法安全删除，应阻止并提示用户等待当前操作结束。

例如：

「当前会话有正在执行的操作，暂时无法删除。请等待操作完成后重试。」

如果 Evaluation Run 已作为独立任务运行，且能够安全脱离 Session，则可以保留 Run 并按既有删除策略处理会话。

### 9.5 删除当前会话后的状态

如果删除的是当前选中的 Session：

1. 清理当前 Session 的消息及临时 UI 状态。
2. 停止或取消该 Session 对应的前端轮询与请求订阅。
3. 清理 URL 中的失效 Session ID。
4. 自动切换到最近一条有效历史会话；如果没有，则显示新会话空状态。
5. 不自动创建新的 Session，除非现有产品逻辑明确要求。
6. 不显示已删除会话的 Proposal、Contract 或 Run 面板。

如果删除的是非当前会话：

- 保持当前对话不变。
- 只更新历史列表。

### 9.6 删除后的列表行为

- 会话数量立即更新。
- 列表保持最近更新时间倒序。
- 已删除会话不再出现在普通列表。
- 刷新页面后仍然不出现。
- 删除操作成功后显示轻量成功提示。
- API 重复删除按现有幂等性规范处理。

### 9.7 测试要求

必须覆盖：

1. 删除普通历史会话成功。
2. 删除当前会话后正确切换。
3. 删除最后一条会话后展示空状态。
4. 取消确认不执行删除。
5. 重复点击不会重复提交。
6. 删除失败显示中文错误。
7. 删除后刷新页面不再出现。
8. 删除 A 数据集版本的会话不影响 B 版本。
9. 删除会话不删除已发布 Contract。
10. 删除会话不删除 Evaluation Run 和 Report。
11. 有正在执行的操作时按规则安全处理。
12. 不存在孤儿外键、错误级联或历史数据污染。
