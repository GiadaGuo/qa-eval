
  根因(有代码证据，非猜测)

  问题不在领域层，而在 ORM 落库顺序。

- EvaluationRunService.create() 中 plan_id = uuid7() 只生成一次，plan 和 run
  共用同一对象，plan 也确实被 session.add()——不存在 UUID
  重复生成或漏写数据库。
- 但真实 Postgres 复现的 SQL 日志显示：flush 只发出了 INSERT INTO
  evaluation_runs，INSERT INTO physical_evaluation_plans 从未发出——run 的
  INSERT 排在了前面，Postgres 逐语句校验 FK 立即失败，路由只捕获
  ValueError，IntegrityError 逃逸成 500。
- 顺序错误的机制:EvaluationRunModel 与 PhysicalEvaluationPlanModel 之间没有
  relationship()(整个 models/ 目录都没有)。SQLAlchemy unit of work 只经
  relationship 建立 mapper 间依赖；无边时按 sort_key = "<module></module>.<ClassName></classname>"
  排序(unitofwork.py:447、mapper.py:709)。同模块下 "EvaluationRunModel" 字典序
  < "PhysicalEvaluationPlanModel"，所以 evaluation_runs 恒定先插，是确定性
  bug。
- 为何测试没发现：现有集成测试用 SQLite 内存库，默认 PRAGMA foreign_keys=OFF
  不校验外键。
- 领域关系确认：契约与 API 入参(EvaluationRunCreate 只收
  contract_version_id)表明 Physical Plan 是创建 Run
  时同事务派生生成的资源，create() 设计本身正确，无需改变 Logical Plan →
  Physical Plan → Evaluation Run 关系。

  修改内容

  文件: src/qa_eval/application/services/evaluation_run_service.py:135-138
  改动: add plan 后先 flush() 再 add run——plan 行先落库满足
  FK，未删任何约束、未加 relationship，符合现有显式 flush 惯例
  ────────────────────────────────────────
  文件: tests/integration/test_evaluation_run_create.py(新增)
  改动: 4 个测试，引擎强制开启外键(PRAGMA foreign_keys=ON):①正常创建(plan+run
  均落库且 FK 满足)②plan 不存在时 run 插入被 FK
  拒绝(IntegrityError，证明约束仍在生效)③事务回滚后 plan/run
  均未残留(原子性)④contract 不存在 → ValueError

  验证结果

- 回归有效性：临时还原旧代码，FK 测试立即失败并复现同一
  IntegrityError;恢复修复后全绿。
- 真实 Postgres 复现脚本：修复后 physical_evaluation_plans 先插入，创建成功。
- 全量测试：146 passed, 6 skipped(MySQL 集成测试按设计需
  RUN_MYSQL_INTEGRATION=1);ruff check / format 均通过。

  一个值得留意的隐患：本仓库所有 ORM 模型都不用
  relationship(),今后任何“同一事务写多张有 FK 关联的表”的代码都会踩同样的坑，且
  SQLite 测试不会兜底——新集成测试建议沿用本次的 FK 强制引擎模式。
